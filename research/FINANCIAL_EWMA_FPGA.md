# Financial EWMA on iCE40UP5K: device and architecture due diligence

6 November 2026. Read `SPEC.md` and the earlier exact-map arithmetic contract. This note assesses a small FPGA fed by a faster event source. It contains analytical budgets, not synthesized results, board benchmarks or trading-profit evidence. Financial workload selection and measured market-event rates are separate obligations.

## What looks plausible

An UP5K can be a useful test of **exact, narrow-state event statistics behind an existing feed handler**, especially when the arrival stream contains bursts, several independent symbols, or a latency-tolerant downstream consumer. A slower fabric clock does not force fewer than one input event per clock: a wide interface can deliver several events together. The actual problem is accepting, storing and executing several *dependent updates of the same state* per clock while preserving the reference rounding and delivering results on time.

The most credible order of investigation is:

1. A multiplier-free exact serial/small-unrolled EWMA on a compact parsed-event interface. This may already solve a modest over-clock arrival ratio.
2. Independent-symbol interleaving and state-memory banking, which are easier than parallelizing one hot symbol's recurrence.
3. Exact block maps for a genuinely hot dependent stream where the first two baselines fail and several microseconds of block delay are acceptable. Small certified/observed K and cheap inverse arithmetic are necessary.
4. Full network reception, book reconstruction and tick-to-trade on this device: a different system project, requiring substantial external front-end functionality. A map accelerator behind such a front end remains plausible, but the full-system cost must be charged to the deployment claim.

## Verified hardware inventory and timing

The [Lattice family selector](https://www.latticesemi.com/Products/FPGAandCPLD/iCE40UltraPlus?ActiveTab=Key+Documents) gives UP5K: **5,280 LUT/flip-flop logic cells, 30 EBR blocks (120 Kibit), four SPRAM blocks (1 Mibit), eight 16×16 multiplier/32-bit accumulator blocks, one PLL**, and 39 user I/O in QFN48 (21 in WLCSP30). The selector's introductory “up to 80 kbits” text conflicts with its own family table; use the table and datasheet, not that introductory sentence. One PLL is correct; third-party lists claiming two should not drive a design.

The [datasheet revision 2.4, February 2025](https://www.latticesemi.com/api/document/download?id=51968), Tables 4.16–4.22, lists: illustrative register-to-register 16-bit adder 100 MHz and pseudo-dual-port EBR 150 MHz; signed 16×16 multiplier bypassing pipeline registers 50 MHz; SPRAM maximum-frequency capability entry 70 MHz in the minimum column; global clock network maximum 185 MHz; PLL output range 16–275 MHz. These numbers have different meanings. The adder/EBR examples are software-generated characterized examples, not a complete application guarantee. Neither PLL range nor clock-network limit certifies a routed recurrence. Its internal oscillator is nominally 48 MHz, not a universal achieved fabric frequency. Architecture/I/O sections list ordinary programmable I/O and hardened SPI/I²C; no native 10G Ethernet transceiver/MAC is provided in this device inventory. This inventory-based conclusion concerns built-in resources, not every possible external bridge.

The [DSP usage guide, FPGA-TN-02007-1.2](https://www.latticesemi.com/view_document?document_id=50669), Sections 2.2–2.4 and Table 2.2, describes configurable input, intermediate multiplier and output registers, 16×16 multiplication and accumulator routing. **Deduction:** an initiation interval of one for *independent products* does not imply one dependent rounded EWMA update per cycle. If state must traverse `q` pipeline stages before its next use, a single state has II at least `q` unless bypassing, unrolling, speculation or interleaving changes the dependency. The accumulator's local addition feedback is not the same operation as multiplying the newly rounded state by `a` on every event. Count external shifts, clipping, widths, input contribution and state-selection logic as well.

No quoted device number establishes a post-route clock for this project. Use **25 MHz and 50 MHz only as explicit hypothetical clocks** until timing analysis of the actual configured paths, operating corner and board interface passes. A 32-bit price/state generally does not fit one 16×16 product; multiple hard multipliers or soft constant arithmetic alter the worker count. Eight DSPs do not mean eight complete arbitrarily wide EWMA engines.

## Ingress is a bus and queue problem before it is a recurrence problem

Let `r` be parsed events/s, `f` fabric cycles/s, `b` useful bits per event and `q=ceil(r/f)` peak lane count. A fully utilized `q`-lane interface requires at least `q*b` payload bits each cycle, plus validity/framing. At hypothetical `f=25 MHz`, `r=50 million events/s`, 16-bit samples need 32 payload pins for a single-data-rate parallel input. A forwarded clock and valid consume at least two more pins; symbol IDs, reset, backpressure and outputs can exhaust QFN48's budget. This is a **stripped scalar demonstrator**, not an exchange-message interface. If parsed records are 64 bits, the same event rate needs 128 payload bits per fabric cycle: a directly wired 128-bit SDR bus is outside this package's pin budget. Serialization/DDR or an external gearbox can change that tradeoff, but needs actual electrical timing, CDC and buffering evidence.

Bit rate and event rate are different dimensions. `10 Gbit/s / 64 bits` is only an imaginary payload ceiling, not an observed financial-event rate; network framing, packet/message lengths, filtering and event aggregation matter. An actual line-rate workload must specify the feed, messages of interest, parser output width, burst envelope and distribution among symbols. Do not set EWMA alpha from the FPGA clock: event-time alpha applies when an event is processed; changing the fabric clock alone does not change that filter. A timestamp-dependent decay can remain in the scalar contract if each event's A/D is known independently of unresolved state, but variable division/control costs then belong in the budget.

An external PHY alone is not automatically a parsed-event source. Explicitly allocate PHY/PCS/MAC, packet handling, sequence/gap detection, message parsing, timestamping and symbol dispatch either to external hardware or the UP5K. If a stronger FPGA/SmartNIC already does all this, explain why moving the EWMA to a second device is useful despite link latency and BOM. A plausible reason must be demonstrated, such as an already available companion/low-power processing interface or an exact-execution experiment, rather than assumed savings.

For a burst arriving at rate `r_hi` for `T` seconds, a server of capacity `mu` needs at least `(r_hi-mu)*T` additional event slots when positive, before accounting for an existing queue. Example: 80 million/s arriving to a 50 million/s engine for 10 microseconds adds 300 events; at 64 bits each that is 2,400 bytes. Finite buffering handles bursts, not indefinitely sustained overload. The output path similarly needs either sufficient per-event bandwidth or an explicitly changed output contract (for example, only block-end statistics).

## Exact arithmetic and the strongest cheap baselines

For the project's single-rounding convex EWMA,

`s_next = clip(floor((A*s + (D-A)*x + B)/D))`,

the coefficient `a=A/D` weights old state and `1-a` weights the new observation. Wide intermediates and signed mathematical floor are required. If B=0 and both states and inputs stay in the same bounded interval, convexity keeps results in that interval, so clipping can be provably inactive. Overflow and multiple truncations can destroy that reasoning.

With `D=2^m`, a forward floor is an arithmetic shift after a sufficiently wide sum. With `A=D-1`, use `(D*s + x-s)/D`, giving `s + floor((x-s)/D)` for single-rounding floor semantics. This needs subtraction, shift and addition rather than a generic multiplier. With negative differences, `trunc((x-s)/D)` is a **different machine**; implementations that discard magnitude bits and move toward the old state require their own monotonicity/threshold analysis. Two independently rounded products also differ from rounding the combined numerator. Do not transplant a published RTL's alpha into the project's contract without inspecting this detail.

Other exact specializations: `A=1` makes the state product trivial; sparse constant A supports shift/add; fixed non-power-of-two inverse division can use constant-divider arithmetic; a sign/Boolean EWMA may have only two reachable states and should be solved as a small FSM/Boolean prefix, not assigned a generic 16-bit map. Rebase prices around a known anchor only if reconstruction, shifts, range and every rounding step are proven equivalent. A small observed range is not automatically a certified state interval.

Exact two-event unrolling literally evaluates `f_1(f_0(s))` with both quantizers present, returning both outputs. It trades a longer combinational feedback path and more hardware for two events per cycle. It is a mandatory baseline for arrival ratios near two. Replacing it by a real-affine coefficient scan usually drops an intermediate quantizer and is not bit-exact. Multi-symbol interleaving hides a pipeline's q-cycle feedback latency only if successive visits to the **same** symbol are q cycles apart; hot-symbol collisions need bypass, stalling or queued exact resolution.

## Map capacity, work and banking

For w-bit state, let `R=2^w-1`. Iterate `W_0=R`, `W_(n+1)=ceil(A*W_n/D)` as a conservative image-width bound. The following 16-bit results were independently computed with integer arithmetic in this review. “Reached” is the first L where the bound takes its eventual plateau value; actual block maps can be narrower.

| a | L reaching bound plateau | Plateau K bound | Ideal eight-worker rate / f, with K at this bound |
|---|---:|---:|---:|
| 1/2 | 16 | 1 | 2 |
| 3/4 | 37 | 3 | 1.333 |
| 15/16 | 139 | 15 | 0.444 |
| 255/256 | 1,564 | 255 | 0.031 |

The last column is **only the assumed arithmetic schedule** `8/(K+3)`, with two endpoint passes, K inverse passes and one replay pass, one transition per clock, no boundary overhead. It is not a device capacity bound or achieved rate. A worker using one DSP and an inverse divider already needs more than one hard block's worth of functionality; shift-specialized workers need not consume one DSP at all. If forward/inverse dependent transitions take `q_f`/`q_i` cycles, replace the work denominator by `3*q_f+K*q_i`, then account for interleaving opportunities explicitly. Inverse `ceil((D*t-C)/A)` is not a cheap power-of-two division merely because forward D is a power of two: its divisor is A.

At hypothetical 25 MHz, the first row's optimistic arithmetic capacity is 50 million events/s. For P=8, L=16, a group has 128 events; filling it at that rate takes 2.56 microseconds and 64 worker cycles also take 2.56 microseconds. Store-and-forward delivery at two events/cycle adds another 2.56 microseconds. Thus a simple non-overlapped **latency budget** is at least 7.68 microseconds plus boundary processing, interfaces and queues, even in this favorable arithmetic example. Overlapping groups needs a valid hardware schedule; adding these stages is not itself evidence of sustained 50 million/s. Exact unrolling may be much better here because the coefficient is so simple.

Raw input storage is `P*L*b` bits, or twice that for double buffering; full replay output storage can cost another similar term. Threshold leaves cost roughly `P*(K*w + base/length metadata)`; a full binary tree has P-1 additional summaries, unless a different boundary schedule avoids retaining all of them. A threshold sentinel `u+1` may need w+1 bits or separate flags; do not silently wrap it. At P=8 and K=25,000, even 16-bit threshold payloads alone require 3.2 Mbits before any tree or inputs, exceeding the device's total embedded memory. K=255 leaf thresholds need about 32.6 Kbits, fitting in capacity but potentially expensive to query/build.

The [SPRAM guide revision 1.4](https://www.latticesemi.com/view_document?document_id=51966), Sections 2 and 4, specifies four 16K×16 **single-port** blocks, width/depth cascading, and no built-in output pipeline registers. Consequently four blocks supply at most four independently addressed 16-bit accesses per clock, before write contention. Width cascading creates a wider word at one address, not extra independent addresses. Note its Section 4.3 “256 KB” wording is a unit typo: 16K×16 is 256 Kbits/32 KiB, consistent with the primitive and datasheet.

The [EBR usage guide FPGA-TN-02002-1.7](https://www.latticesemi.com/view_document?document_id=47775), Sections 3–4, specifies separate read/write ports, synchronous operation and 256×16, 512×8, 1024×4 or 2048×2 organizations per 4-Kbit block. These are useful independent worker banks. P=8 workers needing one independent 16-bit input read each cycle need at least eight suitably banked EBRs, not one large SPRAM. Two adjacent events per cycle into the same block require paired banks/a 32-bit logical word, or a different distribution schedule. Eight independent 32-bit logical worker banks use sixteen EBRs even if most addresses are empty. Separate equally banked replay-output storage uses another sixteen, exceeding thirty before queues. Sharing, in-place reuse, phased writes, smaller distributed buffers or SPRAM staging may recover feasibility, but require a cycle/port schedule and a conflict proof. There is ample raw memory for tiny L; **bank count/ports can fail first**.

K-way parallel comparison requires K thresholds available together, which embedded RAM does not provide through one port. Sequential scanning costs O(K) cycles; binary search costs roughly log2(K+1) dependent memory reads; fully parallel comparators use replicated registers/distributed storage and routing. A small-K boundary engine is realistic; a blanket “one-clock map lookup” assumption is not. Also count ordered replay: P workers naturally generate outputs for different blocks together, while a consumer wanting original global order needs a reorder buffer and enough read bandwidth. Tagged per-symbol output order is a different, sometimes cheaper, contract.

## Existing financial/EMA hardware evidence and reading limits

* **Asheim, Skovhede and Vinter, CPA 2016, “VHDL Generation From Python Synchronous Message Exchange Networks.”** [Author proceedings preprint](https://www.wotug.org/cpa2016/preprints/09-preprint.pdf). Read Section 3.1 and implementation/validation context. It demonstrates two financial EWMA calculators with different decay times, generated VHDL and simulation correspondence to the source model. This establishes an actual financial-EWMA hardware example, not an UP5K benchmark, exchange-rate proof or samplewise-floor map construction. Its narrative timing statements should not be reused as present-day trading latency requirements.
* **Open Research Institute `lowpass_ema`.** [Maintainer repository](https://github.com/OpenResearchInstitute/lowpass_ema). Read README only, not audited RTL. It supplies a public signed fixed-point EMA implementation and mentions financial smoothing. This is a baseline lead, not a validated arithmetic/performance result.
* **Public “HFT” repositories with UART/EMA demos.** [Example maintainer repository](https://github.com/Adityaskumbar/FPGA-HFT-Trading-System). README inspection shows UART packet ingestion and a shift-configured EMA detector. Treat as direct-RTL baseline leads; self-reported nanosecond/profit claims are not performance evidence. Distinguish parser-to-detector cycle counts from wire-to-decision latency.

Native fixed-point leads under separate project audit include a difference-truncated alpha=1/16 implementation and unsigned 17-bit offset-rounded single-affine implementations at feedback coefficients 61/64, 63/64 and 127/128. Their exact quantizer placement matters more than their “EMA” labels. For example, toward-old-state difference truncation may retain 2D-1 distinct fixed states near a constant input; the single-floor convex model's D-1 width plateau cannot simply be reused. Do not count these leads as independently verified by this device note.

## Ranked feasibility and next decision

**High feasibility as an experiment:** a parsed, narrow event stream with precisely specified arithmetic and an artificially reduced 25 MHz fabric clock; compare serial shift/add, exact two-event unroll, independent-symbol interleaving and maps. Artificially reducing clock is useful for studying events/cycle, but does not establish that maps beat the best-clocked baseline or reduce energy.

**Conditional feasibility as a useful financial component:** an existing front end delivers a bounded-burst stream with a hot-state collision pattern that defeats interleaving, exact fixed-point reproduction is required, and the consumer permits the measured block delay. Show a small K under native coefficients/state precision and a complete bank schedule. A block-end-only monitoring/risk statistic can omit full replay, improving feasibility, but changes output granularity and must be stated openly.

**Weak candidate without new evidence:** slow-decay full-range 16–32-bit EWMA requiring every decision with sub-microsecond added delay, fed by an assumed unlimited input bus. Long memory resists certified contraction; widening prices consumes multipliers and pins; external networking can dominate cost. This is a workload mismatch to resolve, not proof that every financial EWMA is unsuitable.

The next gate is a cycle/port spreadsheet plus synthesis of the cheap exact baseline and one small map design, on the same device and arithmetic. Reserve pins and EBR for the chosen ingress/output contract first. Report best achieved clock, per-state II, sustainable and burst event rates, full output delay, LUT/FF/DSP/EBR/SPRAM, worst-case fallback behavior, and front-end cost. Advance the financial claim only when those numbers beat a concrete deployment requirement.
